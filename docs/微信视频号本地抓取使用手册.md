# 微信视频号本地抓取使用手册（仅本地实验）

> 状态：实验性、本地分支专用，**不随 `main` 发布，也不推送到 GitHub**。它依赖 macOS 微信桌面端的实际行为，当前尚不能保证捕获或下载成功。

## 适用范围

本手册用于研究微信聊天中的视频号视频卡片。桥接在用户明确确认后启动本机回环代理，并通过 PAC 仅将 `*.qq.com` 路由至桥接器；除 QQ 域名外，系统的现有网络与代理设置保持不变。桥接停止时会恢复由 DigCrawl 设置的 PAC 并删除其本地 CA。

桥接不导出微信 Cookie、请求体、响应正文或媒体直链。开启页面适配器后，当前视频的播放地址和可选解密信息仅在正在运行的本地桥接进程内存中使用，以执行一次明确确认的本地下载。

## 准备

1. 在本地视频号分支构建当前二进制：`go build -o digcrawl ./cmd/digcrawl`。本分支需要 Go 1.26.1；若默认 `go` 更旧，请使用已安装的 Go 1.26.1 工具链构建，不要修改 `go.mod`。
2. 使用真实微信桌面端登录，并准备一条包含视频号视频卡片的聊天消息。
3. 推荐使用下方的一键命令；仅在诊断时才需要打开两个终端。
4. 一键命令会自动创建会话状态目录与 MP4 输出路径；只有手动诊断时才需要选择状态目录，例如 `/tmp/digcrawl-wechat-channels-test`，且同一次手动试验的所有命令必须使用同一目录。

不要向桥接提供 Wi-Fi 密码、微信密码或代理密码。带用户名/密码的手动上游代理目前会被拒绝；先停止桥接后再恢复或调整此类代理。

## 1. 一键下载与转写（推荐，单终端）

日常使用不需要终端 A/B，也不需要手动关闭或重新启动微信。运行一个前台命令即可：

```bash
./digcrawl wechat-channels capture \
  --yes \
  --transcribe
```

它会启动带页面适配器的本地桥接，并且只将 QQ 域名流量经由回环代理；它不会关闭、重启或唤起微信。命令提示后，在已经打开的微信中重新打开并播放一张视频号卡片即可。每次运行会在当前工作目录的 `storage/digcrawl/wechat-channels-captures/` 下自动创建一个 `时间戳-随机串` 会话目录，并在该 captures 根目录下生成 `wechat_video_时间戳-随机串.mp4`；传给桥接的路径和终端打印的实际路径均为绝对路径。不需要也不建议为一键命令手动指定 `--state-dir` 或 `--out`。桥接成功停止后会删除这个由本次命令创建的会话状态目录，但保留下载的 MP4；停止失败时会保留状态目录，并打印可复制的恢复命令。如需指定下载位置，仍可传入一个不存在的绝对路径，例如 `--out /Users/dig/Downloads/video.mp4`。DigCrawl 会自动等待页面适配器拿到可下载资源，再下载该视频、可选地按现有 ASR 配置转写，并在成功、失败或 Ctrl-C 后尝试恢复由本次桥接设置的代理与证书。

首次使用 `--transcribe` 前，请先执行一次 `./digcrawl asr setup --yes`；命令会在启动桥接前检查 ASR 是否可用。默认最多等待资源出现 10 分钟，可用 `--wait 15m` 调整；资源就绪后的下载默认最多运行 30 分钟，可用 `--download-timeout 45m` 调整。单个视频默认最多写入 2 GiB；可用 `--max-bytes 4294967296` 调整。两者互不影响，避免长视频在刚开始下载时被等待超时取消。下载超时或超出大小上限都不会发布部分 MP4。不带 `--transcribe` 时只下载 MP4。若显式提供 `--out`，它必须是一个此前不存在的绝对路径，避免覆盖已有文件。若配置的 ASR provider 不是 `local`，确认提示会明确说明音频可能离开本机。

## 2. 手动下载验证：启动页面适配器（终端 A，仅调试）

要验证或下载当前视频，**必须**使用 `--page-adapter`。不带该参数的桥接仅能用于元数据导入或原始流量诊断，不能证明下载链路是否可用。

以下是已在真实微信桌面端复验成功的启动方式；终端 A 必须保持运行：

```bash
./digcrawl wechat-channels bridge start \
  --yes \
  --page-adapter \
  --state-dir /tmp/digcrawl-wechat-channels-test \
  --capture-metadata /tmp/wechat-adapter-candidates.ndjson
```

**不需要先退出或重启微信。** PAC 生效后，新发起的网络连接会按 PAC 选择桥接；保持微信打开，直接进入聊天、重新打开目标视频卡片并播放即可。已有的 HTTP/2 长连接和已缓存的页面资源不会被 PAC 强制迁移，因此首次未捕获时，先关闭视频页并重新打开卡片；只有在多次重新打开仍失败时，才将完全退出并重新启动微信作为最后的诊断手段。

`--capture-metadata` 是可选的本地诊断：它只记录候选请求的主机、无查询参数的路径、方法、响应状态、内容类型、内容长度和传输协议，文件权限为 `0600`。它不会记录 Cookie、查询参数或任何正文。视频详情可能由页面运行时回传给适配器而不表现为可见 JSON/媒体请求；因此 NDJSON 中只有 JS/CSS **不表示下载失败**。

每次试验请使用一个此前不存在的诊断文件路径；若路径已存在，桥接会在修改代理前拒绝启动，避免覆盖已有结果。

## 3. 仅导入或原始流量诊断：启动普通桥接（终端 A）

只有在研究元数据导入或原始页面流量时，才使用不带 `--page-adapter` 的普通桥接：

```bash
./digcrawl wechat-channels bridge start \
  --yes \
  --state-dir /tmp/digcrawl-wechat-channels-test
```

首次运行可能要求 macOS 授权安装本地 CA 和调整当前网络服务的代理设置。成功后会显示监听地址 `127.0.0.1:20261`。

如需研究页面初始 HTML，可在**绝对路径**显式开启一次诊断捕获：

```bash
./digcrawl wechat-channels bridge start \
  --yes \
  --state-dir /tmp/digcrawl-wechat-channels-test \
  --capture-page-html /tmp/digcrawl-wechat-channels-page.html
```

该 HTML 可能包含敏感页面状态，只保存在本机且文件权限为 `0600`；研究完成后请自行安全处理，不要提交或上传。

## 4. 在微信中触发请求

1. 微信已打开时无需重启，直接切换到目标聊天；手动桥接启动时若微信未运行，它会被正常唤起；一键命令则要求先打开微信。
2. 重新打开目标聊天中的视频号卡片，点击播放。
3. 等待页面和视频实际开始加载；不要只停留在消息缩略图。
4. 观察终端 A：它会保留捕获统计。若看到 `has not captured a video`，表示本次没有捕获到可导入视频，而不是导入命令本身损坏。

若视频页变成空白、无法播放或网络异常，立即按 Ctrl-C 停止终端 A，再重新打开微信验证网络已恢复。不要在异常状态下重复启动多个桥接器。

## 5. 导入元数据（终端 B，可选）

在同一状态目录中运行：

```bash
./digcrawl wechat-channels import \
  --yes \
  --bridge-state-dir /tmp/digcrawl-wechat-channels-test
```

成功时会先打印当前视频预览，再按配置导出元数据。`404`、`has not captured a video` 或超时都表示当前客户端会话没有提供桥接器可用的当前视频数据；先停止桥接、确认微信可正常播放后再进行一次干净的重新测试。

## 6. 下载当前视频（终端 B，实验性）

确认终端 A 是按第 2 节带 `--page-adapter` 启动的；在微信中重新打开并播放目标卡片后，再在终端 B 执行：

```bash
./digcrawl wechat-channels download \
  --yes \
  --bridge-state-dir /tmp/digcrawl-wechat-channels-test \
  --out /Users/dig/Downloads/wechat-channels-test.mp4
```

`--out` 必须是绝对路径。下载不写入元数据导出；播放 URL 与可选解密信息只在终端 A 对应的桥接进程中保留。下载超时或没有捕获到视频时，停止桥接并恢复网络后再诊断；这不是稳定发布能力。

手动下载同样默认最多运行 30 分钟；可用 `--download-timeout 45m` 调整。单个视频默认最多写入 2 GiB；可用 `--max-bytes 4294967296` 调整。超时或超出大小上限都不会发布部分 MP4，终端 A 会继续保持桥接，便于你选择重试或按 Ctrl-C 停止并恢复代理。

终端 A 与终端 B 应使用同一次构建的当前二进制。当前 CLI 会在下载前检查桥接是否支持有界下载；若出现 `does not support bounded downloads`，说明终端 A 仍是旧桥接。先执行第 8 节的 `bridge stop`，再按第 2 节用当前二进制重新启动带 `--page-adapter` 的桥接，然后重试。不要手动编辑状态文件，也不要为了兼容旧桥接移除 `--max-bytes` 限制。

如果你为 Gateway 或 LocalBrowser 配置了非空 `AllowedDomains` 白名单，读取视频号分享链接时应同时包含 `weixin.qq.com` 和 `channels.weixin.qq.com`：前者通常是分享入口，后者是视频号页面的最终跳转域名。该要求不会自动绕过你设置的白名单。

## 7. 对已下载媒体进行本地内容提取

这一步是通用本地 ASR，不依赖微信桥接。首次使用先安装隔离运行时：

```bash
./digcrawl asr setup --yes
```

然后转写本地文件：

```bash
./digcrawl asr transcribe \
  /Users/dig/Downloads/wechat-channels-test.mp4 \
  --provider local \
  --model small \
  --timeout 1200
```

`--timeout` 是本次任务的时间下限；实际预算会结合媒体时长计算，且绝不会超过配置中的 `ASR.MaxTimeoutSec`（默认 1800 秒）。如果视频较长，需要先提高该配置上限，再重新运行。转写完成后可基于输出文本进行摘要、要点和引用整理。

## 8. 始终停止并恢复（终端 A 或 B）

正常结束时优先在终端 A 按 Ctrl-C。若终端 A 已关闭或需要显式恢复，执行：

```bash
./digcrawl wechat-channels bridge stop \
  --state-dir /tmp/digcrawl-wechat-channels-test
```

命令只会恢复仍由本次 DigCrawl 桥接拥有的代理设置并移除其证书。完成后，验证微信视频页和普通网页都能正常打开；如仍异常，先检查 macOS 当前网络服务的 PAC/代理状态，而不要再次启动桥接。

## 快速诊断清单

| 现象 | 首先处理 |
| --- | --- |
| `404` 或 `has not captured a video` | 在微信中实际播放卡片；确认终端 A 未退出；本次状态目录一致；失败后停止并重新开始一次干净会话。 |
| 微信视频页空白或无法播放 | 立即 `bridge stop` / Ctrl-C，确认 PAC 已恢复后再测试。 |
| 下载超时 | 一键命令中重新打开并播放视频，命令会自动检测并继续下载；手动调试时确认终端 A 按第 2 节带 `--page-adapter` 启动。不要以只含 JS/CSS 的 NDJSON 判断下载失败。 |
| `does not support bounded downloads` | 用同一状态目录停止终端 A 的旧桥接，再用当前二进制重新启动带 `--page-adapter` 的桥接；不要删除状态文件或回退为无上限下载。 |
| 本地转写报 `No module named faster_whisper` | 先运行 `./digcrawl asr setup --yes`，不要把依赖安装到系统 Python。 |
| 转写达到时限 | 检查媒体时长和 `ASR.MaxTimeoutSec`；提高硬上限后重试，而不是只反复增大命令行 `--timeout`。 |

## 不要做的事

- 不要将本手册、抓取日志、HTML、媒体、证书或视频号桥接提交到公开分支。
- 不要为了让桥接工作而把全系统流量改到回环代理；设计边界是仅 `*.qq.com`。
- 不要把捕获失败视作绕过平台访问限制的信号；本功能只用于用户已在本机微信中有权打开的内容研究。
