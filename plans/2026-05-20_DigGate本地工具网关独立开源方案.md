# DigEino 本地采集与通用 Agent 网关独立开源方案

## 1. 背景

DigEino 已完成本地 Gateway、Collector、MCP、stdio 等插件运行时能力升级，也进一步讨论了无宿主本地采集落盘能力，例如：

- `digeino collect <url>`：采集网页、公众号、小红书、抖音、X，并导出 Markdown / HTML / JSON。
- `digeino login` / `digeino connect`：登录宿主并启动本地 Collector，由 Knowledge、DigFlow 或第三方 Agent 下发任务。
- `gateway` / `collector` / `mcp` / `stdio`：通过统一 Tool Manifest、ToolCall、ToolResult 协议暴露本地工具。

继续深入后可以看到两个事实：

1. **无宿主本地采集落盘能力与 Eino 关系不强**
   普通用户只关心把链接保存成本地 Markdown / HTML / JSON，并不关心 Eino、Agent、ToolCall、Gateway 或 Collector。

2. **本地 Gateway 能力也不应绑定 Eino**
   Gateway / Collector / MCP / stdio 的设计目标本来就是面向所有 Agent 编排系统，而不是 DigFlow / Eino 专属。DigEino 只是当前第一个工具 provider 和孵化仓库。

因此，DigEino 中孵化出的能力可以逐步拆成更清晰的三个产品/项目边界：

```text
DigGate / diggate
  通用本地 Agent 工具网关

digeino
  Eino / DigFlow 生态工具 provider 与业务工具库

local-content-collector
  无宿主本地内容采集与落盘 CLI
```

## 2. 核心判断

### 2.1 DigEino 的原始定位

DigEino 可以继续定位为：

```text
面向 Eino / DigFlow 生态的工具集合、Agent 能力库和 provider
```

它沉淀：

- `tools/*` 业务工具。
- Eino Tool 包装。
- DigFlow / Knowledge 相关适配。
- 平台采集 executor 的 provider 实现。

### 2.2 Gateway 的真实定位

Gateway 更像是：

```text
面向所有 Agent 编排系统的本地工具运行时
```

它提供：

- 工具发现：`ToolManifest`
- 工具调用：`ToolCall`
- 工具结果：`ToolResult`
- 本地执行：browser / file / private tools
- 多传输形态：HTTP / WebSocket Collector / MCP / stdio
- 安全边界：工具白名单、域名白名单、权限、审计、Artifact
- Provider 插件化：DigEino 只是一个 provider

### 2.3 Collect 的真实定位

无宿主 `collect` 更像是：

```text
面向普通用户的本地内容采集整理 CLI
```

它提供：

- 单 URL 采集。
- 批量 URL 采集。
- Inbox 模式。
- Markdown / HTML / JSON 导出。
- assets 目录整理。
- Obsidian / Notion / 本地知识库友好输出。

它的用户不一定使用 Eino，也不一定使用任何宿主 Agent。

## 3. 三项目边界建议

### 3.1 `DigGate`

定位：

```text
DigGate: Agent-agnostic Local Tool Gateway
```

面向对象：

- LangChain
- Dify
- Coze
- OpenAI Agents
- Claude Code
- Cursor
- Codex CLI
- DigFlow
- Knowledge
- 自定义 Agent 平台

核心能力：

```text
protocol/
  ToolManifest
  ToolCall
  ToolResult
  Artifact
  wire protocol

runtime/
  registry
  executor
  policy
  audit
  artifact store

transport/
  http
  collector websocket
  mcp
  stdio

provider/
  provider interface
  provider manifest
  provider lifecycle
```

它不应该直接依赖 Eino，也不应该默认假设工具来自 DigEino。仓库名和 CLI 建议统一为 `diggate`。

### 3.2 `digeino`

定位：

```text
Eino / DigFlow tool provider
```

核心能力：

```text
tools/
  research
  browser
  file
  wechat
  platform/xiaohongshu
  platform/douyin
  platform/x

provider/
  digeino provider adapter
  wraps existing tools into gateway entries
```

DigEino 可以依赖 `DigGate`，把自身工具注册为 provider：

```text
digeino tools
        -> digeino provider adapter
        -> DigGate runtime
        -> HTTP / Collector / MCP / stdio
```

### 3.3 `local-content-collector`

定位：

```text
Local content collector and exporter CLI
```

面向对象：

- 普通用户。
- AI 工具重度用户。
- Obsidian / Notion / Markdown 用户。
- 想把网页和社媒内容归档到本地的人。

核心命令：

```bash
collect "https://mp.weixin.qq.com/s/..."
collect "https://www.xiaohongshu.com/explore/..."
collect "https://www.douyin.com/video/..."
collect "https://x.com/user/status/..."
collect --file urls.txt --format md,html,json
collect inbox
```

核心能力：

```text
platform detector
executor caller
markdown exporter
html exporter
json exporter
assets writer
inbox watcher
local index
```

它可以复用 DigEino provider，也可以直接复用 platform extractor 核心库。

## 5. 为什么 Gateway 值得独立

1. **宿主中立**
   其他 Agent 系统不需要接受 DigEino / Eino 生态才能使用本地工具网关。

2. **Provider 中立**
   DigEino、企业私有工具、浏览器工具、文件工具、数据库工具都可以成为 provider。

3. **协议可标准化**
   Tool Manifest / ToolCall / ToolResult / Collector wire protocol 可以沉淀成独立 spec。

4. **开源传播更容易**
   “通用 Local Agent Tool Gateway”比“DigEino 的 gateway 子模块”更容易被理解和采用。

5. **降低业务耦合**
   Gateway 不需要理解 DigFlow、Knowledge、Eino 或具体业务工具，只负责运行时与传输。

## 6. 为什么 Collect 值得独立

1. **普通用户心智更直接**
   用户想要的是：

   ```bash
   collect "https://mp.weixin.qq.com/s/..."
   ```

   然后得到：

   ```text
   文章标题.md
   文章标题.assets/
   ```

2. **不需要宿主**
   用户没有 Knowledge / DigFlow / 企业 Agent 平台时，也能直接使用。

3. **不需要理解 Agent**
   Collect 是本地内容整理工具，不需要讲 Gateway、Collector、ToolCall 等概念。

4. **适合开源增长**
   Markdown、Obsidian、Notion、Claude Code、OpenClaw 用户都可能需要本地内容采集整理。

5. **能反哺平台 Executor**
   Collect 可以作为最小产品闭环，持续验证公众号、小红书、抖音、X 的平台 extractor 质量。

## 7. 短期不建议立刻硬拆

虽然最终边界应该拆清楚，但不建议现在立即物理拆库。

当前更稳的节奏是：

```text
第一步：继续在 DigEino 仓库内孵化
第二步：把包边界切干净
第三步：减少 gateway 对 DigEino config/tools 的直接依赖
第四步：抽象 provider interface
第五步：新增 cmd/digcollect 或 digeino collect 验证本地落盘体验
第六步：API 稳定后拆出独立 repo 开源
```

原因：

- 当前 Gateway 仍直接注册 DigEino executor。
- `gateway/executor` 仍直接引用 `tools/research`。
- `config.Config` 混合了 Gateway、Collector、Tools.LocalBrowser 等配置。
- CLI 入口仍在 `cmd/digeino`。
- Go module 路径仍是 `github.com/originaleric/digeino`。

这些耦合需要先被工程化地拆开。

## 8. 当前耦合点

### 8.1 Gateway 与 DigEino 工具耦合

当前：

```text
gateway/bootstrap.go
  -> executor.BrowserBrowseEntry
  -> executor.WechatArticleReadEntry

gateway/executor/*
  -> tools/research
```

建议演进：

```text
gateway runtime only knows Provider interface
digeino provider registers concrete tools
```

### 8.2 Gateway 与配置耦合

当前：

```text
config.Config
  Gateway
  Collector
  Tools.LocalBrowser
  business configs
```

建议拆分：

```text
gateway.Config
digeino.ProviderConfig
localbrowser.Config
host profile config
```

### 8.3 CLI 命令耦合

当前：

```text
cmd/digeino
  gateway
  collector
  mcp
  stdio
  dev-host
```

建议短期：

```text
cmd/digeino
  保留现有命令
  新增 collect/login/connect

cmd/digcollect
  可选新增轻量入口
```

长期：

```text
diggate CLI
local-content-collector CLI
digeino provider CLI
```

## 9. Provider 接口草案

Gateway 独立的关键是抽象 provider。

示例：

```go
type Provider interface {
    Name() string
    Manifest(ctx context.Context) ([]ToolDescriptor, error)
    Register(ctx context.Context, reg *registry.Registry) error
}
```

或者更直接：

```go
type Provider interface {
    Entries(ctx context.Context) ([]registry.Entry, error)
}
```

DigEino provider：

```go
type DigeinoProvider struct {
    BrowserConfig LocalBrowserConfig
    AllowedReadPaths []string
    ArtifactStore artifact.Store
}

func (p *DigeinoProvider) Entries(ctx context.Context) ([]registry.Entry, error) {
    return []registry.Entry{
        executor.BrowserBrowseEntry(...),
        executor.BrowserSnapshotEntry(...),
        executor.BrowserActionEntry(...),
        executor.WechatArticleReadEntry(...),
        executor.XiaohongshuNoteReadEntry(...),
        executor.DouyinVideoReadEntry(...),
        executor.XPostReadEntry(...),
    }, nil
}
```

这样 Gateway runtime 只加载 provider entry，不关心 entry 来自 Eino、浏览器、企业内网还是第三方插件。

## 10. Collect 架构草案

短期可以在 DigEino 内实现：

```text
cmd/digeino collect
        |
        v
localcollect/
  detector/
  runner/
  exporter/
  filesystem/
        |
        v
gateway/runtime Execute
        |
        v
digeino provider executor
```

调用路径：

```text
digeino collect <url>
  -> detector detects platform
  -> build ToolCall
  -> runtime.Execute
  -> platform executor
  -> ToolResult
  -> exporter writes md/html/json/assets
```

长期拆出：

```text
local-content-collector
  depends on:
    diggate/protocol
    diggate/runtime or lightweight runner
    digeino-provider or platform-core
```

## 11. 开源边界建议

### 11.1 `DigGate` 适合开源

可开源内容：

- 协议类型。
- HTTP / WS Collector / MCP / stdio transport。
- runtime / registry / policy / artifact。
- provider interface。
- 示例 provider。
- dev host。

谨慎内容：

- 强业务工具。
- 私有平台凭证逻辑。
- 与 DigFlow / Knowledge 深度绑定的业务代码。

### 11.2 `local-content-collector` 适合开源

可开源内容：

- CLI。
- URL detector。
- Markdown / HTML / JSON exporter。
- 本地目录组织。
- assets 管理。
- 公众号公开文章采集。
- 插件接口。

谨慎内容：

- 小红书、抖音、X 的强反风控细节。
- 登录态 Cookie 的高风险自动化。
- 批量采集和绕过访问限制相关逻辑。

建议采用：

```text
core open source
platform plugins optional
rate limit and permission built-in
```

### 12.1 Gateway 项目名

最终命名：

```text
项目名：DigGate
仓库名：diggate
CLI：diggate
中文名：DigGate 本地工具网关
Tagline：A local tool gateway for any agent.
```

中文定位：

```text
DigGate 是一个面向任意 Agent 的本地工具网关，用于安全地暴露本地浏览器、本地文件、私有 API、企业内网和桌面能力。
```

## 13. 分阶段路线图

### 阶段一：DigEino 内部孵化

- 保持现有 `gateway` 能力可用。
- 新增平台 Executor：公众号、小红书、抖音、X。
- 新增 `digeino collect <url>`。
- 新增 Markdown exporter。
- 验证本地落盘体验。

### 阶段二：包边界清理

- 抽象 `Provider` 接口。
- 将 DigEino 工具注册移动到 `digeino provider`。
- 将 Gateway 配置与 DigEino 业务配置拆开。
- 将 `protocol`、`runtime`、`transport` 从业务工具中解耦。

### 阶段三：独立 CLI 验证

- 增加 `cmd/digcollect`。
- 增加本地配置目录。
- 增加 `collect --file`、`--format`、`--out`。
- 增加 index 和 assets 管理。

### 阶段四：独立 repo 开源

- 拆出 `diggate`。
- 拆出 `local-content-collector` 或 `digcollect`。
- DigEino 作为 provider 依赖 DigGate。
- Collect 复用 provider 或 platform core。

### 阶段五：生态扩展

- 支持第三方 provider。
- 支持企业私有工具 provider。
- 支持浏览器扩展调用 collect。
- 支持 Obsidian / Notion 导出。
- 支持宿主设备绑定和本地落盘双路径互通。

## 14. 最终目标形态

```text
DigGate / diggate
  A neutral runtime for local tools used by any Agent host.

digeino
  A provider of Eino/DigFlow-oriented tools and platform collectors.

local-content-collector
  A local-first CLI for saving web and social content as Markdown/HTML/JSON.
```

三者关系：

```text
DigGate 是基础设施。
DigEino 是工具 provider。
Collect 是面向普通用户的产品入口。
```

## 15. 结论

DigEino 升级出来的本地 Gateway 已经不是 Eino 特有能力，而是一个通用 Agent 本地工具网关。无宿主 `collect` 能力也不是 Eino 特有能力，而是一个面向普通用户的本地内容采集整理产品。

因此，建议采用“先孵化、后拆分、再开源”的路线：

1. 在 DigEino 内继续验证 Gateway、平台 Executor 和 Collect。
2. 将 Gateway 抽象为 provider 中立、宿主中立的运行时。
3. 将 Collect 抽象为无宿主、本地优先的内容采集 CLI。
4. 当 API 和产品路径稳定后，分别独立开源。

这样既能利用 DigEino 当前已有实现快速前进，又不会把本应通用的基础设施和本地产品能力长期锁在 Eino 语境中。
