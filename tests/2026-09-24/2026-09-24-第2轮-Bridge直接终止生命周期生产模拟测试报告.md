# DigCrawl Bridge 直接终止生命周期生产模拟测试报告（第 2 轮）

- 日期：2026-09-24
- 范围：单机单 profile 的 Bridge stop/restart 进程所有权、子进程回收与替代实例隔离。
- 结论：通过。停止主路径不再依赖 Bridge HTTP shutdown 或浏览器平滑清理；它只终止精确 profile owner 的私有进程组，并在锁与活动组成员均释放后再允许新 owner。原子 owner 记录覆盖了 stop 调用在等待期间异常退出的启动竞争窗口。

## 本轮验收目标

1. `bridge stop` / `bridge restart` 是直接停启，不等待在途读取，也不做滚动交接。
2. 终止范围只能是完整 socket 参数匹配到的 Bridge；不能按泛化进程名处理。
3. Bridge 管理的子进程必须一同终止；生命周期锁、owner 记录中的活动组成员任一存在时不得启动替代实例。
4. 已释放资源的僵尸记录不应把正常重启绑定到 launchd 的回收时机。

## 执行与证据

| 验证 | 结果 | 证据 |
| --- | --- | --- |
| 精确 socket 匹配 | 通过 | `TestBridgePIDRequiresExactSocketArgument` 排除相近 socket 与其他命令。 |
| 旧形态 owner | 通过 | `TestStopKillsExactLegacyBridgePID` 仅终止已验证 PID，不扩大到共享进程组。 |
| 私有进程组与子树 | 通过 | `TestStopKillsExactBridgeProcessGroupAndChild` 以 `setsid` 启动 Bridge helper，再启动模拟 Chrome 子进程；stop 后两者均不再运行且锁释放。 |
| stop 调用异常后的启动门 | 通过（连续 3 次） | `TestStartWaitsForRecordedBridgeGroupAfterOwnerLockRelease` 模拟 owner 锁已释放但记录的组仍运行；启动被阻止，直到该组停止。 |
| 真实启动形态 restart | 通过（连续 3 次） | `TestBridgeRestartReplacesRunningBridge` 经 `NewExecutor` 启动独立 sidecar，restart 后旧 PID 不再运行、新 PID 成为 owner。 |
| Bridge 包稳定性 | 通过（连续 3 次） | `go test ./transport/bridge -count=3`。 |
| Windows 构建 | 通过 | `GOOS=windows GOARCH=amd64 go test -c ./transport/bridge`；Windows 使用完整 socket 匹配加 `taskkill /T /F` 的精确进程树终止。 |

## 边界与残余风险

- macOS 可能短暂保留已死亡的子进程为僵尸记录；它没有执行能力，也不持有 Chrome/profile 锁，因此不作为重启阻塞条件。进程表中仍可运行的状态（包括不可中断等待）会继续阻止替代 Bridge 启动并返回有限超时错误。
- 本机已有的旧 Bridge 已在旧版本生命周期中进入不可中断退出状态，不能由新二进制修复；它仍须由系统回收。新版正常 stop/restart 不以 macOS 重启作为恢复机制。

## 本轮命令
