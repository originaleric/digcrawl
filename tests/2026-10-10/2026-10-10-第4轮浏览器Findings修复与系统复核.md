## 修复前的系统分析

共同问题是策略层与浏览器层对“可以继续、可以成功、必须停止”的判断不一致。browserManager 继续独占连接恢复和资源释放；已有 browseRetryState 继续独占浏览器调用的 deadline、最多一次故障重试和诊断。平台层只决定有限业务回落，不能另设覆盖 Chrome 启动的探测预算，也不能用正文已取得掩盖必要的后续步骤失败。

入口覆盖头条 FetchArticleViaAPI / ReadArticle、通用 BrowserBrowse 的 read/summary/snapshot/screenshot 分支、元数据与媒体辅助步骤、PageFetchJSON 的 GET/POST 成功尾部，以及 provider → Runtime → Bridge → MCP 的错误输出。BrowserAction、独立 BrowserSnapshot、交互登录没有改变执行策略；现有 manager、外部 CDP 隔离、Collector 和平台回落规则仍沿用原实现。

本轮不新增抽象、领域、配置项、恢复服务或持久化状态。使用 Rod 现有 EvalError 类型辨别脚本异常，修改已有媒体 helper 的错误返回；此前单独获批的本机发现 HTTP 包装保持原实现。

## 修复内容

1. **头条 API 4 秒探测时限：已修复。** 删除包住浏览器获取、启动、预热与 fetch 的独立 4 秒 context。API 函数使用已有调用标记，两个端点与 ReadArticle 后续 DOM 回落共享浏览器预算；调用者取消仍立即终止端点链。端点数量仍固定为两个，基础设施失败仍保留原 BrowseError，未增加重试层。
2. **元数据失败仍返回成功：已修复。** 请求了 MetadataScript 时，执行或解析失败返回现有 BrowseError，stage=metadata；null 不满足对象契约，不能冒充完成。所有必要元数据均未验证时不交付部分正文，避免漏掉平台的登录/验证码判断。合法空对象仍允许。媒体监听初始化、媒体探测和结果解析也保留错误；正常无播放器/无媒体的空数组仍有效。DOM 与 API 成功出口均在独立清理结束后核对请求是否已取消，GET/POST 不因尾部取消而重放。
3. **非 JSON fatal 响应：已修复。** 头条先调用原 ClassifyAPIResponse，再辨别响应格式。401/403、429、461/471 无论返回 JSON、HTML、普通文本或空体，均立即终止并保留原业务错误码。200 HTML 等非 fatal 响应仍可有限回落。

修复后的系统复核还发现：新进入统一错误链的脚本异常若包含 EOF、timeout、target closed 等文本，会被原有字符串分类误认为传输故障。已在原分类函数中用 Rod.EvalError 排除这种误判；元数据解析错误不再包含原始值。没有新增错误类型或另一套恢复判断。
