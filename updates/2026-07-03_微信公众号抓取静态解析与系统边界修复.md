# 2026-07-03 · 微信公众号抓取静态解析与系统边界修复

> 依据 [plans/2026-07-03-微信公众号抓取静态解析优先修复方案.md](../plans/2026-07-03-微信公众号抓取静态解析优先修复方案.md) 落地微信公众号文章读取修复。目标链接 `https://mp.weixin.qq.com/s/TLUaZmr3KC2-W7dcKJKu9g` 已通过真实抓取验证，读取通道从长时间 browser 等待切换为 HTTP HTML 静态解析优先。

## 概述

本次修复解决了微信公众号公开文章抓取失败和超时的问题。原实现过度依赖浏览器动态加载，容易卡在微信页面资源、脚本或验证流程上；而目标文章的静态 HTML 已包含标题、正文、作者、发布时间和图片信息。

修复后，微信公众号读取链路调整为：

1. HTTP 静态 HTML 解析优先。
2. 明确风控、验证码、删除、私有、登录等状态快速返回结构化错误。
3. HTTP transient 失败才进入 browser 兜底。
4. HTTP 与 browser 成功结果统一执行标题、正文和最终 URL scope 校验。

---

## 一、根因与证据

### 1.1 失败根因

| 问题 | 影响 |
| --- | --- |
| Browser 路径依赖 `page.WaitLoad()` | 微信页面外链资源、脚本和安全验证流程可能导致长时间等待 |
| 多 selector fallback + retry 叠加 | 单条 URL 失败耗时不可控 |
| 缺少 HTTP 静态解析路径 | 已存在于 HTML 中的正文无法直接使用 |
| 风控页未快速分类 | `/mp/wappoc_appmsgcaptcha` 等页面会被当普通页面继续等待 |

### 1.2 目标链接证据

桌面 Chrome UA 可以获取完整文章 HTML，页面中存在：

- 标题：`《我的起源》玩家共创计划开启 珍稀测试资格优先获取！`
- 作者：`腾讯游戏服务中心`
- 正文容器：`#js_content`
- 文章根节点：`#js_article`
- 发布时间变量：`createTime` / `ct`
- 图片资源：`img[data-src]`

因此该 URL 不是死链，核心问题是读取策略不适配微信公众号页面。

## 二、主要实现

### 2.1 HTTP 静态读取器

新增 `internal/platform/wechat/http_client.go`：

| 能力 | 内容 |
| --- | --- |
| 请求策略 | 桌面 Chrome UA、20s timeout、12MB body limit |
| 成功路径 | 直接解析 HTML 并返回 `platform.Content` |
| 异常分类 | captcha、rate limit、login、deleted、private、not found |
| 诊断 metadata | `read_channel=http`、`extraction_source=html`、`http_status`、`final_url`、`redirect_chain`、`http_parse_state` |
| 兜底策略 | 5xx、timeout、解析不确定等 transient 状态才进入 browser |

### 2.2 HTML 解析器

新增 `internal/platform/wechat/html_parser.go`：

| 字段 | 提取策略 |
| --- | --- |
| title | `#activity-name .js_title_inner` → `#activity-name` → `script.msg_title` |
| author | `#js_name` → `script.nickname` |
| published_at | `#publish_time` → `createTime` → `ct` |
| text | 从 `#js_content` / `.rich_media_content` / `#js_article` 提取纯文本 |
| html | 渲染同一正文 DOM 的清洗 HTML |
| markdown | 由同一 HTML 转换 |
| media | 从同一 DOM 收集 `img[data-src]` / `src` |

为保证输出一致性，`HTML`、`Markdown`、`Text`、`Media` 均来自同一份正文 DOM；图片会从 `data-src` 同步补齐到 `src`，避免 HTML 输出和资源下载列表不一致。

### 2.3 Browser 兜底优化

`internal/platform/wechat/article.go` 调整为：

- `ReadArticle` 先走 HTTP 解析。
- HTTP 明确业务异常直接返回 `platform.ReadError`。
- HTTP transient 或解析不确定才进入 browser。
- 微信 browser 兜底设置 90s 总超时。
- browser selector fallback 收敛为 `#js_article`、`#js_content`、`#img-content`。
- 成功内容统一执行标题、正文、scope 校验。

### 2.4 输出格式修复

`internal/platform/output.go` 修复 `--format md,json,html` 的格式归一化：

- `md` / `markdown` 保留 Markdown。
- `json` 会保留 JSON 中需要的 `text` 与 `markdown`。
- `html` 保留 HTML。

这避免了真实抓取成功但 JSON / Markdown / HTML 某些字段被格式过滤误删。

## 三、系统边界修复

### 3.1 新增 fatal scope 错误

`internal/platform/errors.go` 新增：

- `SCOPE_VIOLATION`

该错误为 fatal，不允许 fallback 或 retry 继续接受内容。

### 3.2 微信最终 URL scope invariant

本次 review 后将 invariant 明确为：

> 微信公众号读取只接受最终仍在微信允许域名内的内容。

覆盖范围：

| 层级 | 行为 |
| --- | --- |
| HTTP 初始 URL | 非 `mp.weixin.qq.com` / `weixin.qq.com` 拒绝 |
| HTTP redirect | 跳出微信允许域名立即 `SCOPE_VIOLATION` |
| HTTP final URL | 最终 URL 跳出微信允许域名立即失败 |
| ReadArticle fallback | HTTP scope violation 后不得进入 browser |
| Browser 内容验收 | `final_url` / `SourceURL` / `CanonicalURL` 任一站外即失败 |

### 3.3 Browser 基础契约修复

review 过程中发现 `BrowserBrowseResponse.URL` 注释为“最终抓取的 URL”，但实现返回的是请求 URL。已在 `internal/browser/browser_browse.go` 修复为使用 `page.Info().URL`。

这避免 metadata 脚本失败时，平台只能看到原始请求 URL，从而绕过最终 URL scope 校验。
